## Final Pixel candidate

The installed APK matched the rebuilt local arm64 APK by SHA-256. Milo J again
received a 403 episode on the initial resume (both audio and video requests),
then recovered automatically: 2.887 s from the open, including 1.680 s after
reload. Its repeat seek to about 5 minutes buffered for 1.145 s; a further
seek to about 11:34 was followed by approximately 85 s of healthy playback.
HOME/PiP, foreground return, and switching to Rusowsky worked. Rusowsky's
first frame was 1.982 s.

Charlie Puth exposed a remaining cold-connection delay: first frame 5.814 s,
despite metadata arriving in 0.790 s. Two tiny initialization responses
(2740 and 5036 bytes) took 4.363/4.437 s, with TTFB 4.325/4.380 s and
`reused=n`. The concurrent preconnect took 4.554 s. Later requests reported
`reused=y` and TTFB 31–92 ms, and playback continued for over 60 s without
media errors. Those slow requests logged protocol `unknown`; the current
telemetry does not split DNS, connect, and TLS times. This establishes a
first-request delay, but cannot attribute it to QUIC, DNS, TLS, or the CDN.

Playback was explicitly paused before handing the phone back. The patch was
not exercised by changing the physical phone's default network; that event
sequence is covered by the local callback regression tests.

## Computer reproduction

An isolated API-32 emulator reproduced a spontaneous audio HTTP 403 on the same
Milo J video, with the failed media load starting at about 60 s. The first open
took 34.845 s to render a frame, including a startup request timeout and
fallback attempts. Android then killed the process during a WebView package
update (`stop com.google.android.webview due to installPackageLI`), so that
episode cannot establish whether playback would have recovered. A subsequent
launch rendered a frame in 6.020 s; Rusowsky then opened in 1.610 s.

The final candidate also passed a 150-second silent outage using
`tools/netshape.py` on the computer emulator. Charlie Puth was opened during
the blackout. Android continued reporting the same validated Wi-Fi network;
the player reached its recovery cap and scheduled the bounded timer retry.
The control script measured 150.1 s using its monotonic clock and recorded
restoration at 10:28:00.667; a first frame rendered at 10:28:05.146,
about 4.5 s later, with no user action. This confirms recovery after an outage
without a connectivity callback. It is one run, not an estimate of worst-case
recovery latency. The shaper used 3000/1000 kbps and 120 ms configured RTT;
other emulator traffic shared the proxy, so these are not throughput or
transport comparison measurements. Proxying also disables the direct QUIC
path.

`PlaybackNetworkFailureTest` reproduces a ranged HTTP 403 through a real
loopback socket and Media3's HTTP data source. It checks that the load policy
surfaces the rejection immediately without requesting a transport change.
No captured signed URL or external request is used by this test.
Its second test checks the existing alternative-transport trigger: a
zero-byte initialization timeout requests failover, while a partial init
download or a midstream timeout retains media retries. This checks the policy,
not the comparative performance of Cronet and regular HTTP.

The next video opened after the simulated outage, Grupo Frontera, rendered a
frame in 1.205 s. The emulator proxy setting was restored to its original
unset state and the task's emulator, local ADB server, capture, and shaper
were stopped afterward.

## Other network methods assessed

Current mobile playback uses embedded Cronet 143.7445.0 plus its existing
regular-HTTP fallback. The mobile source factory does not currently wire
`HttpEngineDataSource`, `OkHttpDataSource`, or `KtorDataSource`.

| Candidate | What it would test | Limit |
| --- | --- | --- |
| OkHttp media data source | A separate HTTP/2 transport for fresh connections | Requires a matched cold-connection comparison; the observed 403 does not demonstrate a transport defect. |
| Android HttpEngine | The platform-managed stack on supported Android versions | Usually uses Cronet internally, so it is not an independent protocol comparison. |
| Media3 Ktor data source | A newly supported networking integration | Arrived in Media3 1.11; this app uses 1.10.1 and has custom live-manifest integration to verify during an upgrade. |

Android documents the HttpEngine and OkHttp options in its
[network-stack guide](https://developer.android.com/media/media3/exoplayer/network-stacks).
The [Media3 1.11 announcement](https://android-developers.googleblog.com/2026/08/media3-1-11-whats-new.html)
introduces the Ktor extension. None was benchmarked in this pass or established
as more reliable. A useful next experiment would record DNS/connect/TLS timing
and compare the same uncached media through the supported transports, keeping
request identity, content, and network constant. Adding client profiles has
no demonstrated benefit from these measurements.

## Recovery change

A capped player could miss a working replacement default network: the old
callback only remembered validation loss or `onLost`, while Android can send
`onAvailable(new)` without `onLost(old)` and stop tracking the old default.
That behavior is documented in the
[Android network callback reference](https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback).

`DefaultNetworkRecoveryCallback` now tracks the default network identity and
requests one recovery after a replacement validates. Replaying the same
healthy network at registration does not retry. Each registration also owns
its cancellation state, so an already-dispatched callback cannot reload a
later video or recovery episode after cancellation.

Twelve callback tests cover replacement validation, an already-validated
handover with no disconnect event, registration replay, duplicate events,
same-network restoration, obsolete-network events, and cancellation before
or during posting. Removing only the new identity edge in an isolated class
copy makes the already-validated handover regression fail; the fixed class
passes. The physical phone's radio was not changed to reproduce this edge.
