# Playback denial and request scheduling — 2026-09-07

## Preserved incident

The Pixel displayed “Inicia sesión para confirmar que no eres un bot” while
opening Rusowsky Tiny Desk (`Fo89b8zAIE4`). The screen showed a black player at
00:00 and the server's reason in the title position. The owner confirmed that
the same video played normally in the official YouTube app.

The relevant request sequence finished at 11:33:12 local time:

- Two existing authenticated player requests returned HTTP 200 with an
  `UNPLAYABLE` playability result and a reload-page reason.
- The following existing player request returned HTTP 200 with
  `LOGIN_REQUIRED` and the explicit Spanish bot-check reason. The request took
  117 ms and used HTTP/2 with TLS 1.3.
- The app recognized the challenge, activated its existing 900-second
  cooldown, and suppressed automatic next-video attempts. Format info
  reached the player 728 ms after the tap, with no media formats.
- No media source was prepared and no media download began. This incident
  therefore does not demonstrate a Cronet/OkHttp media connection failure.

The 15-minute cooldown belongs to the app; it is not evidence of a server ban
of that duration. Successful playback in the official app narrows the observed
denial to NewTube's request/session path but does not establish its cause.
No client identity, fingerprint, token, proxy, authentication or cooldown
changes were made in response to the incident. No external-player UI was added.

## Profile audit

The captured walk already exercised three configured player profiles. The two
account-bearing profiles, `TV_DOWNGRADED` and `TV`, both carried the stored
OAuth authorization and received HTTP 200 responses with an `UNPLAYABLE`
reload-page result. The following anonymous `VISIONOS` request received the
explicit `LOGIN_REQUIRED` bot-check result. The circuit then stopped the walk;
probing the rest of the profile ring after an explicit challenge would add
request pressure without establishing a transport problem.

The three profiles' client names, numeric IDs, versions, user agents and device
context were traced from `AppClient` through `QueryBuilder` and the Retrofit
headers. Each request uses one `AppClient` as the source for both its body and
headers, and the captured header hashes and auth flags agree with that path.
The configured tuples also match the current upstream
[`yt-dlp` client definitions](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/youtube/_base.py).

The capture logged `authUser=n`. That does not establish an OAuth defect:
[Google's documented OAuth request form](https://developers.google.com/youtube/v3/guides/authentication)
requires the bearer `Authorization` header, which was present, while yt-dlp
generates `X-Goog-AuthUser` for its cookie-session path when it has a session
index or delegated account. The
InnerTube player API has no public contract that makes this extra header a safe
device-OAuth change. No profile or auth-header values were modified.

## Eager suggestions after a denial

The phone starts `/next` alongside `/player` to fill the watch page quickly.
In this incident it began 2 ms after the tap and completed after the bot-check
had already reached the player, so related videos appeared on a page whose
video could not play. Declining to start another suggestions request in the
error branch did not cancel this already-running request.

`SuggestionsController.cancelPendingSuggestions()` now disposes the in-flight
metadata work, clears any result that won the race, and resets the eager-load
state so a later explicit video open can fetch normally. The bot-check branch
calls it before leaving the error overlay visible. This reduces unnecessary
work and fixes the inconsistent denial page; it does not claim to change the
server's playability verdict.

## Unnecessary session warmup

`SessionWarmup` could start a throwaway video fetch after the user had already
selected a real video. The previous Pixel trace shows this fetch starting at
11:22:28.508 while the selected video's initialization and first media requests
were running. The user's real selection had reached the playback view about
1.5 seconds earlier.

The repaired scheduler claims feed/fallback scheduling atomically and checks
again after its 1.2-second delay. The playback view signals selection before
loading the video; a speculative job that has not begun now yields to that
selection. Completing real playback setup during the delay also suppresses
the throwaway request, even when the persisted first-run flag was already set.
An already-running warmup is not forcibly interrupted by this change.

The historical setup-complete bit remains a display hint, not proof that
cached setup data is fresh. Idle-browsing warmup still runs so expired caches
can refresh; a full skip based only on that bit could move refresh work onto
the next video tap. Cold-install behavior and existing caches remain available,
and unsuccessful warmup does not create a retry loop.

Twelve local tests cover playback priority, historical versus current
readiness, the post-delay check and concurrent scheduling.

This removes unnecessary work. It is not proof that this work caused the
bot-check, nor that suppressing it will prevent future challenges.

## Obsolete source builds

The shared source-build executor previously generated and parsed every queued
MPD before checking whether its video had been superseded. It now checks the
open generation before starting work and again before delivering the result.
Rapid selections can discard obsolete queued builds without spending their
XML-generation/parsing time ahead of the current video.

Speculative source publication is also atomic with reset/release invalidation,
so a build that finishes late cannot repopulate a cleared source stash. An
already-completed stash matching the newly selected video is still retained
and consumed once. Running XML work is allowed to finish, but stale results
are discarded. No buffer thresholds or playback quality settings changed.

These are local scheduling fixes. Their live TTFF benefit and effect on
rejection frequency have not been established by this incident capture.
