# Optional SABR VOD source — implementation and comparisons

**Unreleased experiment after 1.8.0. DASH remains the default.** SABR now
delivers real YouTube media and plays on the Pixel; it is **slower to first
frame** than DASH and **uses fewer bytes**. See the section immediately below —
everything after it is the earlier round, kept as history, and its "no
successful delivery" conclusion is superseded.

## Delivery works: the 403 was the CLIENT, not the protocol (2026-09-08, later)

### What the 403 actually was

The first implementation gated SABR on an authenticated, server-logged-in
**TVHTML5** response. That is the one route whose media is dead, so the gate
could only ever select the failing case.

Reproduced off-device from this laptop — a different network, a different IP and
an anonymous identity, one video (`Fo89b8zAIE4`), one session, **no PO token of
any kind** — POSTing each response's own `serverAbrStreamingUrl` with the app's
request shape:

| /player client | adaptive formats with URLs | SABR endpoint | SABR media POST |
| --- | ---: | --- | --- |
| **VISIONOS** | 23 | yes | **HTTP 200, 133,605 B of UMP MEDIA** |
| **IOS** | 0 (SABR-only) | yes | **HTTP 200, 133,605 B** |
| **ANDROID_VR** | 22 | yes | **HTTP 200, 133,605 B** |
| **ANDROID** | 0 (SABR-only) | yes | **HTTP 200, 133,605 B** |
| TVHTML5 7.x | 0 (SABR-only) | yes | **HTTP 403, zero-byte body** |
| TVHTML5 5.x (`TV_DOWNGRADED`) | 22 | **no SABR at all** | — |

Demuxed from the VISIONOS response, the returned bytes are ordinary fragmented
MP4: `ffprobe` reads H.264 640×360 and AAC 44.1 kHz stereo. So the 403 is a
property of the TV client — yt-dlp marks that family GVS-PO-token-required and
this port cannot mint one — and it is the same wall HANDOFF §26 recorded for
TVHTML5's ordinary media URLs. It is not the phone, the account, the carrier,
the UMP parser or the request encoding.

Copying the VISIONOS endpoint but claiming `TVHTML5` in the request's
`streamerContext` returns HTTP 200 with **zero** media, so the server does check
that the client matches the endpoint it issued.

### Three defects, all of which had to be fixed

1. **Eligibility selected the dead route.** `SabrVodCapability.isEligible` now
   gates on `AppClient.isSabrSupported` — the clients measured above — and no
   longer requires the account. The TV family stays excluded, so its existing
   SABR-only quarantine verdict is unchanged.
2. **A video request asked for a track type that does not exist.** The code sent
   `enabledTrackTypesBitfield = 2` for video, read as a bitfield. Sweeping the
   field against real YouTube: `1` returns audio ALONE, and `0`, `2` and `3` all
   return audio AND video. There is no video-only value, so every video response
   carried an unrequested audio format and the parser terminated the source with
   `unexpected_format` on the first real response. A video request now names the
   companion audio the period is already fetching and declares it fully buffered
   — the protocol's own way to say "do not send me this". Without the claim the
   server adds 188,265 B of its own default Opus per video request; with it the
   companion costs one 2,180-byte init segment and, once the format is in
   `selectedFormatIds`, nothing. Foreign-format parts are now discarded rather
   than fatal, and are never handed to the extractor.
3. **A media-free response was treated as terminal.** The server PACES delivery:
   once the client is far enough ahead of the playhead it answers with control
   parts and no media. Measured off-device — after ~30 s of audio was buffered at
   playhead 0, the next request returned 740 bytes of `SELECTABLE_FORMATS` /
   `STREAM_PROTECTION_STATUS` / `REQUEST_IDENTIFIER`. That is a wait. It is what
   killed the first successful device run one second after its first frame
   (`no_media_progress`, first frame 944 ms, ~10 s buffered, then stop). The
   source now backs off (250 ms doubling to 4 s, reset on progress) and only
   fails when a stream has nothing left to play — three such responses while
   starving is still terminal.

Also fixed: `ATTESTATION_PENDING` is no longer terminal (the iOS client returns
status 2 alongside media that is being served normally; VISIONOS returns 1), and
client names are upper-cased into the protocol enum so `"iOS"` resolves.

### Measured on the Pixel 9, real YouTube, Wi-Fi

`Fo89b8zAIE4`, `debug.arc.player_client=VISIONOS` so both arms use the same
client and the fallback ring cannot confound them, OkHttp for both, byte cache
bypassed, speculative warmups suppressed. Two cells per source in ABBA order,
three opens each = **6 opens per source, 12 in total**. Every open advanced
through 8 s of media and then made a backward and a forward paused seek.

**All 12 opens selected the identical formats** — video itag 136 (1280×720 AVC)
and audio itag 140 (AAC) — so the byte figures compare like with like. **All 12
had zero rebuffers and zero dropped frames.**

| Median of 6 opens | DASH | SABR | SABR vs DASH |
| --- | ---: | ---: | ---: |
| Source-open to first frame | **267 ms** | 333 ms | **+24.7 %** |
| Source-open to READY | **286.5 ms** | 348.5 ms | +21.6 % |
| App UID bytes received | 4,590,625 | **4,099,509** | **−10.7 %** |
| Process CPU | **5,269 ms** | 5,519 ms | +4.8 % |

Individual first-frame values, ms — DASH `178, 185, 241, 293, 399, 438`; SABR
`313, 314, 327, 339, 481, 527`. The distributions overlap only at their tails,
so the startup gap is the more solid of the two findings; the byte gap is the
more consistent (DASH returned 4,590,625 B in four of six opens).

**So: SABR costs about 66 ms of startup and saves about 490 KB per eight seconds
of 720p playback.** That is the honest summary of this round.

### What this does and does not establish

- It **does** establish real SABR delivery, rendering, sustained playback through
  8 s, and working paused seeks in both directions on real YouTube media.
- The byte counter is the process-wide UID counter: it includes concurrent
  loading and metadata, not only the eight seconds of media. CPU includes a
  debuggable process and the harness. Neither is a battery measurement.
- One video, one Wi-Fi network, one device, six opens per arm. No soak, no
  cellular arm, no ABR-adaptation comparison, no live/DVR support (still
  excluded), no long-video or quality-switch soak on real media.
- The client was **pinned**. Unpinned, the phone's ring answered this video with
  `TV_DOWNGRADED`, which has DASH formats and no SABR endpoint at all, so SABR
  engages only once the ring reaches VISIONOS. Enabling the preference does not
  change which client wins.
- The strategic point is not speed. `IOS`, `ANDROID` and `TVHTML5` already return
  **zero** formats with URLs — they are SABR-only today. `VISIONOS` and
  `ANDROID_VR` still hand out URLs. A working SABR source is what keeps those
  routes usable if VISIONOS follows.

Keep the preference **off by default**.

### SABR as a fallback (2026-09-08, later still)

Delivery working is not the same as SABR being *reachable* when it is needed. A
response whose adaptive formats carry no URL - the only case a fallback exists
for - never reached the decoder: `containsAdaptiveVideoInfo()` reports such a
list as "no adaptive video", so `containsSabrFormats()` was false and
`VideoLoaderController`'s `openSabr` branch never ran, while `isUnplayable()`
already consulted the capability and said "playable". Enabling SABR turned
"skip to the next video" into "sit with no source". The only way SABR ever ran
was by displacing a DASH route that already worked.

Fixed in three places: the DTO publishes a link-less adaptive list as adaptive
when the capability accepts it; the preference splits into **fallback** (carries
link-less responses) and **preferred** (the byte-saving experiment that
displaces working links); and a failing *fallback* source defers to the normal
client recovery instead of ending playback. Measured matrix, four Tiny Desk
videos on the Pixel 9: see HANDOFF §28.

Result: on the normal ring nothing changes (`type=dash-mpd`, first frame, no
403), and a link-less IOS response now reaches `prepare type=sabr-vod` on 4/4
opens instead of being skipped. It does not finish there - and the reason is not
the request.

**The ~60 s attestation wall.** `RELOAD_PLAYER_RESPONSE` was a symptom. Running
the app's own request builder through a new instrumentation diagnostic
(`SabrReloadDiagnosticTest`) shows an IOS request at position 0 returning real
media on all four videos; what failed in playback were the loads issued after
`position-discontinuity reason=seek from=0 to=1029273`, the watch-history resume.
Sweeping the start position on three videos, fresh anonymous session per arm:

| start position | IOS / ANDROID_VR | VISIONOS |
|---|---|---|
| 0 s | media, `ATTESTATION_PENDING` | media, status **OK** |
| 30 s | media, `ATTESTATION_PENDING` | media, **OK** |
| 60 s+ | **no media**, `ATTESTATION_REQUIRED max_retries=10` | media, **OK** |

The wall is between **56.2 s and 60.0 s** on all three videos, and it is
positional rather than a session quota - a fresh session asking for 60 s is
refused, one asking for 0 s six times running is served every time.
`ATTESTATION_REQUIRED` is the PO-token demand this port cannot mint. Since the
fallback only ever sees link-less clients, and those are the walled ones, the
fallback is capped at the first minute of any video.

**Both roles ship OFF.** The fallback was written default-on and flipped the
same day: it has never carried a video that would not otherwise play (seven
unpinned opens never reached a link-less client; the media 403 that does occur
is rescued by the existing ring walk, on a client with no SABR endpoint), it
costs the ring a client plus four recovery attempts, and the wall above means it
cannot be repaired by tuning the request.

**The measured byte comparison was wrong twice over.** The original "~11% fewer
bytes" compared prefetch, not efficiency: at 8 s played DASH had buffered 58.7 s
to SABR's 32.0 s. Per minute of media actually fetched, SABR cost 8.9 MB against
DASH's 5.8 (+55%) - because the companion-audio suppression never worked. The
whole-track buffered claim is silently ignored unless
`start_segment_index`/`end_segment_index` are set, so every video response
carried a duplicate 63,583-byte audio segment that the audio stream then fetched
again. With the indices set the companion costs a 2,324-byte init segment and the
response drops from 103,962 to 42,605 bytes. Re-measured on cellular (4 videos, 3
opens per arm, identical itag 136 + 140, zero rebuffers): SABR **5.1 MB/min vs
DASH 5.8** - parity, -9% to +7% per video, first frame ~60 ms slower. There is no
data-saver case; the fix simply stops the insurance path wasting half its
bandwidth. See HANDOFF section 28b.

**The decoder itself is sound, and VISIONOS is unwalled.** Status `OK` at every
position including the final seconds. On the Pixel 9 with the experiment on:
`prepare type=sabr-vod` -> `first-frame +2369` -> still `PLAYING` at **2:34**,
3:00 buffered, zero `stream_protection` / `response_reload_required` /
`SabrException` lines over three and a half minutes. If the default is ever
reopened, the opt-in experiment on VISIONOS is the path that works - not the
fallback.

### What the additional controlled tests are worth

They test local source/decoder behavior and expose implementation costs. They
do not model YouTube's server scheduling/packaging, authorization, HTTP/TLS/QUIC,
radio behavior or server-side ABR, and cannot answer whether SABR improves real
YouTube playback.

Completed **32 measured opens and 64 paused/resumed seeks**, four opens per
source per profile, on the Pixel. Each profile used two excluded warmups followed
by DASH/SABR/SABR/DASH twice on one engine. The input was the same generated
60-second 1280×720/24 fps AVC (~2.02 Mbps) plus mono AAC (~96 kbps), fixed quality.
Each measured open advanced through eight seconds of media, then sought backward
to 2 s and forward to 52 s; both seeks retained pause and subsequently advanced.
These short runs are not a soak or an automatic-quality-adaptation comparison.

An in-memory link charged per-request latency and one shared A/V response-byte
budget using 8 KiB receive blocks. Server UMP framing was prepared before timing
for both arms. POST bodies were counted but not upload-shaped; headers were not
modeled. The interruption was a six-second delivery pause triggered near media
position 2 s, not packet loss or a real radio handover.

Medians in milliseconds, **DASH / SABR**:

| Simulated downlink / request latency | First frame | Backward seek first frame | Forward seek first frame | Rebuffer time through 8 s of media |
| --- | ---: | ---: | ---: | ---: |
| 20 Mbps / 20 ms | 210 / 247 | 91.5 / 156.5 | 101.5 / 167.5 | 0 / 0 |
| 4 Mbps / 80 ms | 416 / 523 | 92 / 414.5 | 300 / 424.5 | 0 / 0 |
| 1.5 Mbps / 160 ms | 910.5 / 968 | 97 / 856.5 | 609.5 / 807 | 4321.5 / 6022 |
| 3 Mbps / 80 ms + six-second pause | 481 / 488 | 82.5 / 464 | 335.5 / 453.5 | 6120 / 6300.5 |

The constrained link is deliberately below the encoded bitrate, so both sources
stall. All opens had zero player errors; dropped-frame totals were DASH/SABR
6/5 on the constrained profile and 5/5 on the interruption profile, zero on the
other two. This is not a blanket zero-dropped-frames result.

The backward-seek gap identifies a real implementation tradeoff: stock DASH can
reuse retained samples, while this SABR implementation clears protocol/sample
state on every seek. That is a future optimization candidate, not evidence about
YouTube's server. Forward seeks also differ in whether the target is still buffered;
the per-run buffered positions are recorded, not assumed equal after a reset.

[All 96 measurement rows](SABR-COMPARISON-2026-09-08.csv) include READY, decoded
frames, buffer positions, response/POST-body bytes, requests and process CPU time.
Byte totals include different amounts of prefetch; seek byte counters include
concurrent loading, not exclusively seek-caused traffic. CPU includes a debuggable
process and the fixture harness. Neither metric establishes real data/battery savings.

## What is implemented

- Independent `:sabr-media3` library on the existing **Media3 1.10.1**. It uses
  Loader, SampleQueue and unmodified MP4/WebM extractors/decoders, not the deleted
  ExoPlayer fork. Protocol definitions and Apache notices have
  [documented provenance](../../sabr-media3/PROVENANCE.md) and are included in APK assets.
- Settings: **“Prefer SABR when available (experimental; next VOD)”**, with an
  equivalent Spanish label. The persisted preference defaults false and changes
  apply to the next open. Debug property overrides are absent from release DEX.
- Only already-accepted, server-authenticated TV ordinary-VOD responses with
  supported A/V identities and SABR endpoint/configuration qualify. Denials,
  bot checks, live/post-live/DVR and unsupported metadata keep their existing
  classification. Ineligible metadata does not become a SABR request.
- The format DTO now preserves full `itag/lmt/xtags` and audio-track identity.
  Audio groups remain separate by language, track identity and DRC; the adapter
  does not invent original/dubbed labels. Selection is resolved by group/index,
  not merely by itag or equal public Format values.
- Initial metadata/init-only responses, media continuations, bounded opaque
  policy/context state, actual playhead/bandwidth/buffer ranges and EOS handling.
  Response framing is bounded to 32 MiB, controls to 64 KiB, and requests to a
  20-second deadline. Unknown controls, identity mismatches and malformed/truncated
  data terminate the source. Signed query encoding is preserved except `rn`.
- Forward/backward and paused seeks discard the old generation before new samples
  can be read. Adaptive quality changes preserve **actual old-quality buffered
  ranges** while reinitializing the new format; manual stream replacement starts
  cleanly. Release/cancellation closes the old requests.
- Existing media **OkHttp** pool/proxy/TLS, constructed lazily only when selected.
  No account headers/interceptors, redirects or POST replay; no immutable DASH
  byte-cache use for stateful responses. SABR does not yet use Cronet.
- Lazy stock Media3 sidecar subtitles, fetched only when selected. A tiny
  version-pinned package bridge accesses Media3's package-private lazy factory;
  it does not replace any AndroidX class. Run caption tests on Media3 upgrades.
- Source failures are terminal and visibly actionable. Generic long-buffering,
  quality/client recovery, reconnect callbacks and retry timers cannot take over.
  An explicit Play tap can retry the normal metadata path without invoking the
  generic client/token-switch circuit. No automatic alternate source on denial.

This closes a decoder/source capability gap. It is **not** a new server-side ABR
algorithm, universal SABR-client support, an authorization fix or evidence that
SABR saves bytes/battery. Media3 still chooses the requested quality.
